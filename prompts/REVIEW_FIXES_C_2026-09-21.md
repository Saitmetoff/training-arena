## Final read-only auth-review finding to close first

`AccountController._runSignIn` invalidates the generation when B sign-in starts but retains A's `_session` and signedIn status. A call to accessToken AFTER B starts can therefore begin A's refresh using B's new generation and gateway epoch. B completes, then this late A refresh passes both guards and replaces B's persisted/in-memory token while the profile remains B. Existing tests start A refresh BEFORE B, which misses this window. Make the prior identity unavailable while establishing a new one (or bind refresh ownership to the actual captured identity), and add the exact controlled HTTP/store/controller regression: A signed in -> B sign-in pending -> A token requested/refresh attempted -> B succeeds -> delayed A response -> current and freshly restored identity must both remain B. Do not patch only the display. Keep failed server deletion retry and ordinary sign-in behavior. Run the focused auth tests after this correction, then proceed with push below.

## Confirmed defects

1. `NotificationService._lastRegisteredToken` deduplicates by token alone. `ArenaApp._onViewerChanged` updates the battle viewer only. Account A -> logout -> B with the same device token skips B registration; the server still associates it with A. There is no effective unregister/deactivation path. Registration/rotation requests in flight also need account ownership protection. Define and enforce the authenticated account lifecycle once at the composition/service boundary: logout/deletion deactivates delivery, a new account registers, stale A completions cannot mark B registered or restore A delivery, and a token rotation during registration is eventually registered. Keep retry on temporary failure, no secrets in logs. Reuse existing server register/upsert and provider invalidation if those suffice; add a narrowly scoped unregister API/migration only if necessary, with ownership checks and tests. Avoid a framework or speculative notification features.

2. `PushBridge.currentPermissionStatus()` returns notDetermined with no Firebase configuration, but `requestPermission()` still shows the API33 dialog and marks KEY_REQUESTED. Dart can also show the rationale when config flag/Supabase are present but Firebase is absent. Expose/consume real capability and prevent both rationale and native request/asked-state changes for unavailable push. Preserve normal allow/deny and ask-once behavior when configured. Test enabled-but-unconfigured separately from disabled.

3. Native delivery ignores `ARENA_FEATURE_PUSH_NOTIFICATIONS=false`. Gradle applies Google Services solely on file presence, and ArenaMessagingService posts messages unconditionally. SDK notification payloads can display in the background before Dart runs. A push-enabled -> push-disabled upgrade with retained Firebase configuration/token must not initialize/register/deliver notifications merely because the dependency/config exists. Enforce the same build flag in native configuration/components and bridge/service paths before delivery. Do not rely only on `isAutoInitEnabled=false`: retained tokens and SDK background display are part of this failure. Inspect the final merged manifest for disabled builds. Keep default false, reject ambiguous native/Dart flag disagreement, and keep configured enabled builds compilable.

4. Shared-device privacy: a pending old-account push must not display or route as a new account's notification after logout/switch. The dispatcher currently emits FCM `notification` plus `data` and SDK background auto-display bypasses application checks. Trace payload ownership and the native background path as part of (1)/(3), choosing the smallest safe design. Do not log token/user secrets or place bearer tokens in payloads. Keep existing best-effort inbox behavior and exact request/match tap routing.
