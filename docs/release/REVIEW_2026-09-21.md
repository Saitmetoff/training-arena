## Standards

1. **P1 - ranked release default violates the documented hold.** `.github/workflows/release-checks.yml` enables ranked matchmaking despite the native-push interface decision requiring it to remain disabled pending two-device validation. Configuring release secrets must not silently remove this hold.
2. **P1 - downloaded-tool integrity is checked too late.** `tools/release/check_android_bundle.mjs` records a SHA-256 mismatch but still returns and executes the JAR. Explicit/environment JAR paths also bypass verification. Abort before any execution and verify every supported path against the pinned digest.
3. **P2 - missing Firebase still permits a permission dialog.** `PushBridge.requestPermission` lacks the availability guard used by its status method. This contradicts the documented no-push behavior and can persist an asked state for an unavailable feature.

No actionable style-only findings. Missing owner configuration, physical evidence and media approval are launch blockers, not code-quality violations.

## Spec

1. **P1 - a stale verification can select the wrong account for deletion.** The public deletion client accepts a late account-A verification after restart for B; mutable UI identity can then label the confirmation B. A mocked-fetch reproduction confirmed the subsequent deletion uses A's bearer. Invalidate stale operations and bind the destructive confirmation to the verified identity.
2. **P1 - push registration does not follow account changes.** Token-only deduplication and missing deactivation/rebinding leave a shared device associated with A after B signs in. Cover logout, deletion, account switches and in-flight registration/rotation.
3. **P1 - release workflow enables ranked play before required evidence.** This independently violates the L06 launch task's hold. It is the same code defect as Standards finding 1, not an additional independent defect.
4. **P1 - disabled push can still deliver natively.** Firebase configuration and native components can receive/display messages before Dart observes its disabled flag, including SDK background notification payloads. Enforce the feature boundary on the native delivery path and account ownership.
5. **P2 - unavailable push exposes permission UX.** Both the Dart rationale and native request must respect actual capability, including flag-enabled builds without Firebase configuration. This overlaps Standards finding 3.
6. **P1 - deletion ignores the API envelope.** Every HTTP 2xx is treated as success, including `200 {data:null,error:{...}}`, clearing retry state and announcing deletion. The backend contract supports business errors at HTTP 200. The parser bug is reproduced with a mock; no real server conflict trigger is claimed. Require a valid successful envelope.

## Additional coordinator findings

- Failed legacy preference removal can be reported as successful secure-session deletion, allowing a restart to restore credentials from plaintext. Cached preference state can hide the failed disk removal on retry.
- Overlapping migration, refresh/sign-in and logout need lifecycle ordering; delayed older work must not restore credentials or replace a newer account.
- Cold PKCE restoration discards retryable state on transport/server failure. A consumed authorization code must not be advertised as reusable after a successful exchange followed by storage failure.
- The preview guard regression does not prove eligible readiness or await asynchronous rep delivery. Add a valid positive control and observable state assertions.
- The device storage test deletes the production secure-storage namespace. Synthetic verification must use isolated storage.
